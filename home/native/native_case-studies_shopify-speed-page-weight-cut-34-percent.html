The problem

The owner's own words were that mobile still did not pass page speed on product pages. The store was not slow at the server. Measured three times, the server answered in 0.28 to 0.35 seconds, with Shopify processing a request in 29 to 36 milliseconds. The time was going somewhere else.

Lighthouse on the live homepage said the same from the user's side: a mobile score of 49, largest content paint at 4.1 seconds, 2.2 seconds of blocked main thread, and 19.7 seconds before the page was fully interactive.

What was inside the page

Homepage document: 1,165,391 bytes

Inline scripts: 41 blocks, 493,504 bytes

Inline styles: 28 blocks, 216,062 bytes

Stylesheet links: 38, of which 8 were duplicates

One trust-badge app: 586,647 bytes in every page, half of the whole homepage

What that app drew: On the homepage, one empty 0 by 0 element. On product pages, a thin shipping bar.

How it unfolded

Measure: Page weight and timing on the live store

Document size, every inline script and style block, server time and Lighthouse, so every later claim had a baseline.

Find: One app injecting half the page

A 401 KB script plus the same 61.8 KB stylesheet written three times, on every page.

Decide: The owner chose

Switching the app off removes the bar on product pages, so it was the owner's call. The owner chose the fastest version and asked for a better way to show shipping.

Ship: Published inside the rush window

Checked first that the live theme had not changed since the backup, then published and re-measured.

Follow-on: The menu

Mobile still lagged. The owner's menu had just over a thousand links, written into every page twice, once for the phone drawer and once for the desktop bar.

What we did with Claude

Measure before touching anything

Claude pulled the live theme fresh, measured the homepage with matched sessions and recorded the baseline in numbers, so the result could be shown rather than claimed.

Correct our own first guess

Our first note to the owner blamed the server. Measured directly, the server was fast, so the diagnosis changed to what it really was: page weight and blocking work.

Offer options, do not decide for the owner

The badge bar had real content on product pages, so removing it was a business choice. Claude built the speed copy and told him exactly what he would lose.

Prove the swap was safe

Before publishing, the live theme and the backup were compared file by file and showed no drift. The change list was the app switch plus the theme update and nothing else, with the owner's own settings untouched.

Re-measure on the live store

Page weight was measured again after publishing against the untouched backup theme as the control.

Check your own store

Open a product page, view the page source and look at its size. Over about 1 MB of HTML usually means something is writing code into every page.

Search the source for the names of your apps. An app that appears hundreds of times is the first suspect.

Ask what each heavy app draws on the page. If the answer is nothing, or something you could do in the theme, it is a candidate to remove.

Check how many links your menu has. Large menus are often written into the page twice.

Measure before and after on the same page and the same connection, and keep a backup theme so the change is reversible.

What we learned

Measure the server before blaming it

A fast server and a slow page point at weight and blocking work, not hosting.

Separate what is measurable from what is a choice

The numbers decided that the app was heavy. Only the owner could decide the bar was not worth it.

Say what you did not re-run

Quoting only measured numbers is what makes the rest believable.
