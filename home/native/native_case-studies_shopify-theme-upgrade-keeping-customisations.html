The problem

The owner asked for the update to the next release before a speed pass, then, on the same day, asked for the major version that Shopify had released 40 minutes earlier. A store with its own edits cannot simply install a newer theme: that replaces the edits.

The risk is not the code you can see. It is the owner's translations, menu structure and section settings, which live in files that a careless update overwrites.

How it unfolded

Step 1: Three-way comparison

The live store was pulled fresh and compared with the stock version it came from and the stock version it was going to.

Step 2: Every file classified

Untouched by the store, customised by the store, merchant data, new, or removed upstream.

Step 3: Merge, then check

Only the safe classes were changed, then every locale file was re-parsed and the key counts compared.

Step 4: Second upgrade, same method

The major version went through the same classification on the same copy.

Step 5: Approval and publish

The owner approved in writing, the live theme was re-checked for drift, and the result was verified live.

What we did with Claude

Classify before changing

In the first upgrade, 98 files changed upstream, 93 store files were customised and 131 files belonged to apps or custom code. Of 75 apparent conflicts, 54 were translation files, 13 were owner template settings and only 8 were real code.

Take stock files verbatim when the store never touched them

Each file was first proven byte-identical to the stock version on the live store, so there was nothing of the owner's to lose.

Merge the rest by hand

For the major version, 4 files came verbatim, 2 needed a three-way merge, and translation files were additive only: 80 keys added, 0 changed, 0 removed.

Never write merchant data

Settings and layout files were left alone. A key-by-key diff of the one settings file showed exactly one difference, the app switch the owner had chosen.

Keep what is harmless

The new version dropped 15 classic customer-account files. The store was already on the new accounts, so they were inert, but deleting them gained nothing and could break something. They stayed.

Check your own store

Find out how far behind your theme is. Ask your developer, or check your theme's documentation, for the version you are on and the latest release.

Never update a customised theme by uploading a new copy over it. Ask for a comparison of your files against the stock version first.

List which files hold your own content, such as templates, settings and translations, and ask how they will be protected.

Ask for a backup theme you can republish in one click, and a preview link before anything goes live.

Result

Two upgrades merged and published on one preview and one approval.

No owner template, settings or translation file overwritten.

The store's own speed work and the upgrade landed together, so there was one change to approve instead of two.

What we learned

Classify the files first

Most apparent conflicts were translation files and settings, not code. Sorting them cut real work to 8 files.

Additive beats overwrite

Adding keys and keeping removed-but-harmless files avoids silent breakage.

One preview, one approval

Combining related changes reduces the owner's decisions to one.
