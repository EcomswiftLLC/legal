Shoppers from Facebook and Instagram ads were adding items twice

The page hung and the cart added every item twice, but only for people arriving from Meta ads. The cause was in the order the theme loads its own code.

The problem

Visitors who arrive from Facebook and Instagram ads open the store inside Meta's built-in browser. For them, the page loaded forever on some taps and the cart ended up with two of the same item.

It happened only on that traffic, which is the traffic the owner was paying for. And Meta's in-app browser cannot be run on a desktop, so we could not reproduce it by simply opening the store.

How it unfolded

Read: The theme's loading order

Claude read how the theme loads and runs its cart code.

Cause: The cart script ships late and from another server

The add to cart handler lives in a 214 KB bundle served from the theme vendor's server, loaded deferred.

Fix: A parse-time safety net

A tiny script that runs before the shopper can tap, so a late bundle can no longer cause a double add.

Verify: Simulated the failure

We blocked the vendor's script server in the browser's developer tools to recreate the condition.

Cover: Every add to cart path

A first version covered the main product form. Checking found bundle and landing products use a different button, so the guard became page-level.

What we did with Claude

Work out the cause without the device

Meta's in-app browser was not available, so Claude derived the cause from the theme's code. If the cart script has not loaded when the shopper taps, the browser sends the form the old way, as a full page navigation. The page seems to load forever while the script stalls, and every extra tap sends another add.

Make the safety net stay out of the way

When the theme's script loads normally, the guard does nothing and the theme behaves exactly as before. When it does not load, the guard adds the item once and sends the shopper to the cart.

Reproduce the failure on purpose

Blocking the theme vendor's server in the developer tools recreated a late or missing script, and both bad behaviours appeared, then disappeared with the guard.

Find the path we had missed

Our first version was live for the main products only. Claude found that bundle and landing products add to cart through a separate form. Rather than cover them one by one, we replaced the guard with one that watches every add to cart form on the site.

Have the code reviewed

A second Claude model reviewed the final script before it went live.

Check your own store

Open your store from a link inside Facebook or Instagram on a real phone and add something to the cart. Compare with Safari or Chrome.

Look in your theme for scripts loaded from another company's server. They can be slow or blocked in some browsers.

Check every route to the cart: product pages, bundles, landing pages and the sticky add to cart bar.

Keep tracking and cart fixes separate. A cart guard should never change what your pixel records.

Result

One add per tap, with or without the theme's script, on every product template.

The owner tested the preview before anything was published.

A named rollback theme, so the change could be reversed in one step.

We have not claimed a conversion lift: the fix removes a known failure, and we asked the owner to confirm from real Meta traffic.

What we learned

Recreate the failure on purpose

If you cannot run the real browser, reproduce the condition that causes the bug.

Cover the path, not the page

A guard on one form misses the others. A guard on the behaviour covers them all.

Keep the guard invisible

A safety net should do nothing when the normal path works.
